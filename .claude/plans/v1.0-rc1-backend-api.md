# Plan: v1.0 RC1 — Backend API + PostgreSQL

## Overview

Build the backend API foundation (`apps/api`) with PostgreSQL, Drizzle ORM, and Fastify. 
Do not modify the existing frontend — this is purely the backend layer that the frontend will later connect to page by page.

## Architecture

| Layer | Choice | Why |
|-------|--------|-----|
| HTTP framework | **Fastify** | Lighter than Express, built-in TypeScript support, fast serialization, plugin architecture |
| ORM | **Drizzle** | Type-safe, lightweight, no code generation step, excellent PostgreSQL support, works great with Fastify |
| Database | **PostgreSQL 16** | Via Docker (same Docker setup used for Mosquitto MQTT broker) |
| Validation | **Zod** + Drizzle schema | Drizzle's schema doubles as validation; Zod for request validation |
| Auth | **JWT** (`@fastify/jwt`) | Stateless auth, works with existing frontend `api-client.ts` Bearer token |
| Dev runner | **tsx** | Same pattern as `apps/realtime` — no build step needed for dev |

## Database Schema

All tables map 1:1 to the existing `@sentience/types` interfaces:

### users
- id (uuid PK), email (unique), password_hash, name, avatar, role_id (FK → roles), is_active, mfa_enabled, customer_id (FK → customers), last_login, created_at, updated_at

### roles
- id (uuid PK), name (unique: admin|support|installer|customer), label, description

### role_permissions
- id (uuid PK), role_id (FK), resource, action (create|read|update|delete|manage), conditions (jsonb)

### customers
- id (uuid PK), name, logo, domain, contact_name, contact_email, contact_phone, address, city, country, is_active, license_type, max_devices, max_users, device_count, user_count, estate_count, created_at, updated_at

### estates
- id (uuid PK), name, address, city, region, country, contact_name, contact_email, contact_phone, manager_id (FK → users), customer_id (FK → customers), site_count, device_count, online_count, offline_count, fault_count, warning_count, health_score, created_at, updated_at

### sites
- id (uuid PK), name, estate_id (FK), address, building_count, floor_count, room_count, device_count, online_count, offline_count, fault_count, warning_count, health_score, created_at, updated_at

### devices
- id (uuid PK), serial_number, mac_address, name, type, status, firmware_version, firmware_build, firmware_released_at, firmware_installed_at, battery, voltage, temperature, signal_strength, uptime, last_heartbeat, site_id (FK), room_id, installed_at, last_maintenance, notes, tags (jsonb), created_at, updated_at

### events
- id (uuid PK), title, description, severity, category, device_id (FK), site_id (FK), estate_id (FK), customer_id (FK), user_id (FK), metadata (jsonb), occurred_at, created_at

### alerts
- id (uuid PK), title, description, severity, status, category, device_id (FK), site_id (FK), estate_id (FK), customer_id (FK), assigned_to (FK → users), acknowledged_by (FK → users), acknowledged_at, resolved_by (FK → users), resolved_at, resolution, source, occurred_at, created_at, updated_at

### audit_logs
- id (uuid PK), user_id (FK), user_name, user_role, action, resource, resource_id, description, details (jsonb), ip_address, user_agent, created_at

### reports
- id (uuid PK), name, type, status, format, date_range_start, date_range_end, filters (jsonb), metrics (jsonb), generated_by (FK → users), generated_at, file_url, created_at

### api_keys
- id (uuid PK), name, key_hash, masked_key, status, created_by (FK → users), expires_at, last_used_at, request_count, created_at

### settings
- id (uuid PK), key (unique), value (jsonb), category, description, updated_at

## API Routes

All routes prefixed with `/api` (matching frontend's `NEXT_PUBLIC_API_URL`):

### Public
- `GET /api/health` → { status, uptime, db } 

### Auth
- `POST /api/auth/login` → { email, password } → { token, user }

### Protected (JWT required)
- `GET /api/users` — list users (admin only)
- `GET /api/users/:id` — get user
- `POST /api/users` — create user (admin only)
- `PATCH /api/users/:id` — update user
- `DELETE /api/users/:id` — deactivate user (admin only)

- `GET /api/roles` — list roles
- `GET /api/roles/:id` — get role with permissions

- `GET /api/devices` — list devices (filterable by site_id, estate_id, status, type)
- `GET /api/devices/:id` — get device with telemetry
- `PATCH /api/devices/:id` — update device

- `GET /api/events` — list events (filterable by severity, category, device_id, date range)
- `GET /api/events/:id` — get event

- `GET /api/alerts` — list alerts (filterable by severity, status, category)
- `GET /api/alerts/:id` — get alert
- `PATCH /api/alerts/:id` — acknowledge/resolve alert

- `GET /api/reports` — list reports
- `POST /api/reports` — generate report (placeholder returning mock structure)

- `GET /api/settings` — get all settings
- `PATCH /api/settings/:key` — update setting

## Migration Strategy

Use Drizzle Kit for migrations:
1. Define schema in `src/db/schema/*.ts`
2. Generate migration: `drizzle-kit generate`
3. Apply migration: `drizzle-kit migrate`
4. Seed: `tsx src/db/seed.ts`

## Implementation Order

1. Create `apps/api/package.json`, `tsconfig.json`, `drizzle.config.ts`, `.env.example`
2. Create `apps/api/docker-compose.yml` for PostgreSQL
3. Define all Drizzle schema files
4. Create Drizzle client + connection setup
5. Create Fastify app entry point with plugin registration
6. Build auth middleware (JWT)
7. Implement all route handlers
8. Create seed script with matching demo data
9. Add root-level convenience scripts to `package.json`
10. Update `turbo.json` to include `@sentience/api` in pipeline
11. Write `docs/backend-api.md`
12. Update `ROADMAP.md`, `CHANGELOG.md`, `TECHNICAL_DEBT.md`
13. Run `pnpm lint && pnpm build` to verify

## What We WON'T Do

- No new frontend pages or modifications
- No frontend migration to use the API yet (future sprint)
- No authentication backend UI — API returns JWT tokens, frontend will connect later
- No real-time WebSocket endpoints on the API — the `apps/realtime` bridge handles that
- No Kubernetes, Redis, or other infrastructure
- No E2E tests for the API (unit tests via Vitest are fine but not required for RC1)
